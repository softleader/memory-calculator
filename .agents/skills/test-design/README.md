# test-design

讓 agent 寫出來的每個測試只為真實的 break 而紅：程式錯會紅，沒錯不會紅。跟 agent 預設的寫法差在：每個測試都要說得出哪個真實的錯誤會讓它紅；期望值不能來自被測程式；等待要等可觀察的條件，不是猜一段時間。

## When to use

- 你用 AI coding agent 寫程式，但常拿到「綠燈卻證明不了什麼」的測試。
- 你的 CI 在機器忙的時候會紅，沒人改程式，重跑就過。
- 你刻意改了產品行為，測試跟著紅，要判斷該改測試還是改程式。
- Agent 要新增或修改測試、加 mock、stub、fake，或加測試用的 helper、等待與清理。
- 你想知道某個測試到底能不能失敗，或 review 時想指出一個測試驗的是決定而不是行為。

Agent 動到任何測試之前會自己載入，只改一個期望值或等待時間也算；也可以直接呼叫。

## Getting started

安裝後，描述要測的行為即可，例如：

```text
spec 說付款閘道 30 秒沒回應就放棄，請實作並補測試。
這個表單金額小於等於 0 要擋下來並顯示錯誤，幫我補測試。
這份測試裡的 mock 是不是讓它永遠不會失敗？
這個測試在 CI 偶爾紅，本機都過，幫我看它在哪裡猜時間。
```

## What it catches

常見的問題分成幾種：

- **只驗 spec 的字面內容**：寫了 timeout 30 秒，就斷言設定值等於 30；寫了按鈕文字，就斷言畫面上有那段字。
- **測試自己證明自己**：期望值用被測程式算出來，或只斷言 mock 有被呼叫。
- **錯誤分支沒測到**：mock 永遠成功，錯誤處理的分支從來沒跑過。
- **靠猜時間等系統**：用 sleep 或幾百毫秒的 idle timeout 等系統到位，機器一忙就紅。
- **狀態沒清乾淨**：測試留下檔案或全域狀態，換個順序跑就紅。
- **紅了只改等待方式**：加長 timeout 或掛 retry，沒有找出失敗原因。

這份標準把這些問題變成 agent 寫測試前後都要過的檢查。交付時還要附上：

- **Mutation 清單**：每個合理的錯誤，對應哪個測試會紅。
- **等待與清理的說明**：會等、會 poll、碰外部程序的測試，除了 break 還有什麼能讓它紅，以及各自怎麼釘住。

## It's working if

- 動手前 agent 先說每個測試抓的是哪個改動；說不出來的測試不會出現。
- 期望值是 literal 或手算的 fixture；diff 裡找不到用被測程式算出期望值的地方。
- spec 裡的設定值沒有被讀回來斷言，測的是它改變的行為。
- mock 只出現在慢或外部的那一層；測錯誤處理時，mock 會丟那個錯。
- 等待都等可觀察的條件，放棄以 runner 給測試的時限為準、留時間清理，失敗時交代等的是什麼、最後看到什麼；只有時間本身是受測行為時，才用經過多久判斷結果。
- 測試自己建自己的狀態、結束時收乾淨；單跑、整套跑、換順序跑結果一樣。
- 完成回報附一張 mutation 清單，每個合理的錯誤對應哪個測試會紅；測試抓不到的錯誤，包括被其他路徑補救掉的，標 `unprotected` 並說明原因。
- 測試數量跟著行為走：trivial 的 getter、constructor 沒有測試。

## Common questions

**我的專案不是 Java 或 JavaScript，要先補一份語言對照才能用嗎？**

不用。規則在任何 stack 照原文適用；`SKILL.md` 末尾只收了四條規則擋不住的工具陷阱（ArchUnit 下的 `verify()`、Spring 設定值、mock 掉的 repository、`vi.mock` 整個模組），其他 stack 的陷阱在真實 repo 看到再加一行。原本按語言平行的兩份對照檔，對照實驗顯示不影響結果，已併進這段清單（#481）。

**它會叫 agent 用什麼方式放大負載或打亂順序來重跑？**

不會。skill 只要求會等、會 poll、碰外部程序的測試，在完成回報裡說出除了 break 還有什麼能讓它紅、各自怎麼釘住；有 runner 時附上重跑的指令與次數。用 busy loop、限制 CPU、`-count` 還是 shuffle，是各 repo 自己的工具文件該寫的。

## Limitations

- 負載下或換順序重跑通過，只是跑過的那些情境的證據，不證明任何負載下都不會紅；真正的驗收在真實 repo 的 CI。
- 這份標準不執行 mutation testing 工具（PIT、Stryker）。mutation 清單是 agent 推理的結果，是「它檢查過什麼」的證據，不是工具量出來的分數。
- 渲染出的文字只有在使用者得讀它才知道怎麼做時（錯誤訊息、法律聲明）才當契約斷言；只因 spec 寫了標籤文字就斷言它，會被視為測決定。
- 它只規範測試的設計，不規範寫測試的順序。先寫測試或先寫程式都適用，和 TDD 類的流程 skill 並存。
